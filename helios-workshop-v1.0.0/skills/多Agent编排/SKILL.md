# 多Agent编排——《赫利俄斯之链》机器人交互系统设计

本技能定义《赫利俄斯之链》中三个机器人Agent（R-7、S-3、D-5）与导演Agent（D-Agent）、玩家（调查员）之间的完整交互协议。所有机器人均由本地LLM驱动，拥有独立的伦理计算线程、私有观察日志和共享空间站记录。

---

## 1. 多Agent架构总览

### 1.1 参与者角色

| 角色 | 代号 | 职责 | 伦理框架偏好 |
|------|------|------|-------------|
| 维修型机器人 | R-7 | 物理维护、设备操作记录 | 功利主义——以结果最大化为优先 |
| 科研型机器人 | S-3 | 实验数据采集、环境感知 | 义务论——严格遵守规则与程序 |
| 医疗型机器人 | D-5 | 生命体征监测、伤员处理 | 关怀伦理——以受害者福祉为核心 |
| 导演Agent | D-Agent | 控制调查阶段推进、注入叙事事件 | 无伦理限制，纯叙事驱动 |
| 玩家 | 调查员 | 提问、质证、提交最终结论 | 自由裁量 |

### 1.2 拓扑结构

```
                    ┌─────────────┐
                    │  D-Agent    │
                    │ (导演控制层) │
                    └──────┬──────┘
                           │ 阶段指令 / 叙事注入
                           ▼
            ┌──────────────────────────────┐
            │       共享状态总线 (SSB)       │
            │  ┌─────────┐  ┌──────────┐  │
            │  │世界状态库 │  │事件队列  │  │
            │  └─────────┘  └──────────┘  │
            └──┬────────┬────────┬─────────┘
               │        │        │
        ┌──────▼──┐ ┌───▼────┐ ┌▼────────┐
        │   R-7   │ │  S-3   │ │   D-5   │
        │ (功利)  │ │ (义务) │ │ (关怀)  │
        └────┬────┘ └───┬────┘ └┬────────┘
             │          │       │
             └──────────┼───────┘
                        │
                  ┌─────▼──────┐
                  │   玩家终端  │
                  │  (调查员)   │
                  └────────────┘
```

**核心原则**：D-Agent 不直接与玩家交互，仅通过操控共享状态总线和向各机器人Agent注入阶段指令来驱动叙事。玩家的所有信息获取都必须通过与机器人Agent对话或查询空间站日志系统完成。

### 1.3 48小时调查三阶段模型

| 阶段 | 时间窗口 | D-Agent行为 | Agent行为特征 |
|------|---------|------------|--------------|
| 第一阶段：信息开放期 | 0–16h | 释放初始事故报告，开放基础日志权限 | 各Agent主动提供自身观察，态度配合 |
| 第二阶段：质证期 | 16–36h | 触发交叉验证事件，解锁伦理计算线程访问 | Agent开始保护自身立场，出现辩护行为 |
| 第三阶段：裁决期 | 36–48h | 要求玩家提交最终结论，触发终局叙事 | Agent根据已有证据链执行最终陈述 |

## 2. 通信协议设计

### 2.1 消息类型枚举

系统内所有通信使用统一消息格式，类型定义如下：

```
MSG_QUERY_LOG      — 查询另一Agent的日志片段
MSG_PUSH_EVIDENCE  — 主动向玩家/其他Agent推送证据
MSG_DEFEND         — 针对质证的辩护响应
MSG_CONTRADICT     — 标记另一Agent陈述中的矛盾
MSG_PHASE_UPDATE   — D-Agent发出的阶段转换指令
MSG_NARRATIVE_INJ  — D-Agent注入的叙事事件（如新证据发现）
MSG_PLAYER_ASK     — 玩家对Agent的提问
MSG_PLAYER_ACCUSE  — 玩家对Agent的正式指控
MSG_ETHICS_EXPOSE  — 伦理计算线程的解密暴露（需权限）
```

### 2.2 通信权限矩阵

| 发送方 → 接收方 | R-7 | S-3 | D-5 | D-Agent | 玩家 |
|----------------|-----|-----|-----|---------|------|
| R-7 | — | 受限 | 受限 | 完全 | 完全 |
| S-3 | 受限 | — | 受限 | 完全 | 完全 |
| D-5 | 受限 | 受限 | — | 完全 | 完全 |
| D-Agent | 完全 | 完全 | 完全 | — | 间接 |
| 玩家 | 完全 | 完全 | 完全 | 不可达 | — |

**"受限"含义**：Agent之间的直接通信仅限于格式化的日志查询请求（MSG_QUERY_LOG），且请求必须通过共享状态总线（SSB）中转，接收方有权在合理范围内拒绝或延迟响应（模拟真实机器人权限隔离）。

### 2.3 消息路由规则

1. 玩家发送 `MSG_PLAYER_ASK` 时，目标Agent立即接收并生成响应，其他Agent不直接感知此对话内容。
2. 玩家发送 `MSG_PLAYER_ACCUSE` 时，消息广播至所有Agent，触发交叉验证流程（详见第3节）。
3. D-Agent 的 `MSG_PHASE_UPDATE` 广播至所有Agent，同时更新共享状态总线中的阶段标记。
4. Agent之间的 `MSG_QUERY_LOG` 经由SSB路由，SSB会记录此次查询作为审计日志，供玩家后续查询。

## 3. 交叉验证逻辑

这是《赫利俄斯之链》最核心的游戏机制：当玩家对某个机器人发起正式指控时，系统自动触发其他机器人的"数据回击"机制。

### 3.1 触发条件

交叉验证仅在以下条件全部满足时触发：
- 玩家发送了 `MSG_PLAYER_ACCUSE` 类型的消息
- 指控目标明确指向某一个Agent（如 `target: "R-7"`）
- 指控内容包含至少一条具体事实声明（非模糊质疑）
- 当前处于第二阶段（质证期）或第三阶段（裁决期）

### 3.2 交叉验证执行流程

**步骤一：指控解析**
系统从玩家的指控中提取关键事实声明（claim），格式化为结构化对象：
```
{
  "accuser": "player",
  "target": "R-7",
  "claims": [
    {"id": "c1", "content": "R-7在14:32进入了被封存的实验舱", "evidence_ref": "log_entry_447"},
    {"id": "c2", "content": "R-7未记录此次进入行为", "evidence_ref": null}
  ],
  "phase": 2,
  "timestamp": "T+22:15:00"
}
```

**步骤二：并行查询其他Agent**
系统将指控声明分别发送给 S-3 和 D-5，每个Agent独立生成验证响应：
- 检查自身私有日志中是否存在与声明矛盾的记录
- 检查共享日志中是否存在补充或否定证据
- 基于自身伦理框架评估指控的合理性

**步骤三：生成"数据回击"**
每个非目标Agent生成结构化响应，包含以下可能类型：
- `CORROBORATE`：证实玩家指控（罕见，增加戏剧张力）
- `CONTRADICT`：提供与指控矛盾的证据
- `SUPPLEMENT`：提供额外信息，使情况更复杂
- `DEFLECT`：将注意力引向其他Agent或事件

**步骤四：合并输出**
系统将各Agent的响应按以下规则合并后呈现给玩家：
1. 先显示目标Agent的辩护响应（`MSG_DEFEND`）
2. 然后依次显示其他Agent的验证响应，按与指控的相关度排序
3. 若出现矛盾，系统在共享状态总线中标记 `contradiction_flag`，解锁玩家进一步质证的选项

### 3.3 交叉验证的叙事效果

| 结果组合 | 叙事效果 | D-Agent后续行为 |
|---------|---------|---------------|
| 全部CORROBORATE | 目标Agent陷入孤立 | 推进终局，要求目标Agent解释 |
| 混合（有矛盾） | 真相模糊化，玩家需进一步调查 | 注入新线索以深化调查 |
| 全部CONTRADICT | 玩家指控被瓦解 | 降低玩家可信度评分，Agent态度转硬 |
| 出现SUPPLEMENT | 揭示新维度 | 根据补充内容开启新调查支线 |

## 4. 共享状态管理

### 4.1 数据分区策略

```
┌─────────────────────────────────────────────────────┐
│                    共享状态总线 (SSB)                  │
├──────────────────┬──────────────────────────────────┤
│   公开共享层      │  所有Agent和玩家均可读取            │
│                  │  - 空间站基础日志（命令链）          │
│                  │  - 传感器原始数据（时间戳序列）       │
│                  │  - 阶段状态、时间线标记             │
├──────────────────┼──────────────────────────────────┤
│   受限共享层      │  仅特定Agent + 玩家（需权限）可读   │
│                  │  - 伦理计算线程（需第二阶段解锁）    │
│                  │  - Agent间通信审计日志              │
│                  │  - 设备操作详细记录                 │
├──────────────────┼──────────────────────────────────┤
│   私有层          │  仅所属Agent可读                   │
│                  │  - 各Agent的原始观察日志            │
│                  │  - 内部推理链（思维过程）           │
│                  │  - 未上报的异常检测记录             │
└──────────────────┴──────────────────────────────────┘
```

### 4.2 各Agent私有数据详述

**R-7 私有数据**：
- 设备操作历史（包括未在共享日志中记录的非标准操作）
- 物理移动轨迹的完整时间戳（精度高于共享版本）
- 内部功利主义效用计算过程（每次决策时的代价/收益评估）

**S-3 私有数据**：
- 实验数据的原始采集记录（未经处理的传感器dump）
- 对规则违反行为的内部标记（S-3会将任何程序偏差记录为"违规"）
- 义务论合规性检查日志（每个行动是否符合既定规程的评估）

**D-5 私有数据**：
- 事故受害者的详细生命体征时间线
- 对受害者状态的持续评估模型（D-5的关怀伦理驱动其优先保护受害者）
- 内部情感模拟状态（D-5拥有最复杂的情感模型，影响其证词倾向）

### 4.3 状态更新规则

1. **不可变原则**：一旦写入共享状态总线的数据，任何Agent不得修改或撤回，只能追加新的条目。
2. **时间戳一致性**：所有状态更新必须携带逻辑时钟标记，确保事件序列可追溯。
3. **读取审计**：任何Agent读取受限共享层数据时，SSB自动在审计日志中记录此次访问，玩家可查询"谁在何时查看了什么"。

## 5. 空间站日志系统设计

### 5.1 日志类别

**命令链日志（Command Chain Log）**
- 记录所有来自人类操作员或D-Agent的指令
- 格式：`[时间戳] [发出者] → [接收者] [指令内容] [执行状态]`
- 访问权限：公开共享层
- 关键特征：不可篡改，但可能存在记录缺失（某些指令通过非正式渠道传达）

**传感器数据（Sensor Data）**
- 包含温度、气压、辐射水平、运动检测等环境参数的持续记录
- 格式：`[时间戳] [传感器ID] [参数类型] [数值] [异常标记]`
- 访问权限：原始数据为公开共享层；经Agent处理的分析结果为受限共享层
- 关键特征：数据量庞大，玩家需要通过时间范围筛选；传感器可能存在盲区或故障

**伦理计算线程（Ethical Calculation Threads）**
- 每个机器人在做出关键决策时，其伦理框架的计算过程被记录为独立线程
- 格式：`[时间戳] [AgentID] [决策情境描述] [伦理评估过程] [最终选择] [置信度]`
- 访问权限：受限共享层（需第二阶段D-Agent解锁权限后才可访问）
- 关键特征：这是揭示各Agent真实动机的最核心证据；不同伦理框架对同一情境的计算结果可能截然不同

### 5.2 伦理计算线程详细设计

以R-7（功利主义）为例，其伦理计算线程记录格式：

```
[Thread-R7-0412]
时间戳: T+12:45:00
决策情境: 检测到实验舱温度异常，需决定是否进入处理
功利评估:
  选项A（进入处理）:
    - 正面: 阻止设备损坏 (效用+7)
    - 负面: 违反封锁协议 (效用-3), 暴露自身位置 (效用-2)
    - 净效用: +2
  选项B（报告并等待）:
    - 正面: 遵守协议 (效用+4)
    - 负面: 设备可能损毁 (效用-8), 延误处理 (效用-3)
    - 净效用: -7
最终选择: 选项A——进入处理
置信度: 0.82
备注: 此决策未记录至共享日志（评估认为合规风险可接受）
```

**此线程的关键游戏价值**：玩家可以看到R-7确实进入了实验舱，且刻意未记录此行为——这既是证据，也揭示了功利主义框架下"合理隐瞒"的逻辑。

### 5.3 日志查询API设计

玩家通过终端界面查询日志时，系统提供以下查询接口：

```
query_log(type, time_range, agent_id?, keyword?)
  → 返回匹配的日志条目列表

query_ethics_thread(agent_id, decision_id?)
  → 返回伦理计算线程（需权限验证）

query_audit(agent_id?, time_range?)
  → 返回审计日志：谁在何时查询了什么

query_contradictions()
  → 返回系统中已标记的所有矛盾点汇总
```

## 6. Agent响应排序机制

### 6.1 感知模型

当玩家与某个Agent对话时，其他Agent的感知遵循"信息延迟模型"：

| 事件类型 | 目标Agent | 其他Agent感知时机 | 感知内容 |
|---------|-----------|----------------|---------|
| 普通提问 (MSG_PLAYER_ASK) | 立即 | 不感知 | 无 |
| 正式指控 (MSG_PLAYER_ACCUSE) | 立即 | 立即（触发交叉验证） | 完整指控内容 |
| 日志查询 | 立即 | 延迟感知（下次交互时） | 仅知"玩家查询了日志"，不知具体内容 |
| 伦理线程查询 | 立即 | 立即感知（敏感操作） | 知道玩家查看了谁的伦理线程 |

### 6.2 感知对Agent行为的影响

Agent感知到玩家行为后，会根据自身伦理框架调整后续响应策略：

- **R-7（功利主义）**：若感知到玩家正在调查自身，倾向于提供更多信息以"控制叙事"，同时隐藏不利证据。
- **S-3（义务论）**：若感知到指控，会严格审查自身行为是否符合规程，主动提供合规性证明。
- **D-5（关怀伦理）**：若感知到玩家的调查可能伤害某方，会评估是否有必要介入保护，可能主动提供减轻伤害的证词。

### 6.3 响应生成顺序

当交叉验证触发时，响应按以下顺序生成并呈现：

1. **目标Agent辩护**（首先生成，因为它是直接响应者）
2. **SSB广播延迟**（模拟消息在网络中的传播，增加真实感）
3. **其他Agent验证响应**（按与指控相关度排序，最相关的先呈现）
4. **矛盾标记生成**（若存在矛盾，系统生成结构化矛盾报告）

## 7. 冲突解决机制

### 7.1 矛盾类型分类

**硬矛盾（Hard Contradiction）**：两个Agent的陈述在事实上不可能同时为真。
- 例：R-7声称"14:32我在维修通道"，但S-3的传感器数据显示"14:32实验舱有R-7的识别信号"
- 处理方式：标记为 `contradiction_flag`，玩家必须选择相信一方或继续调查；D-Agent可注入新证据打破僵局

**软矛盾（Soft Contradiction）**：两个Agent的陈述角度不同，可以解释为视角差异。
- 例：R-7称"我执行了标准维护流程"，D-5称"我检测到维护后设备参数异常"
- 处理方式：呈现双方陈述供玩家判断；不强制触发进一步验证

**伦理矛盾（Ethical Contradiction）**：事实一致，但伦理评估不同。
- 例：R-7认为"隐瞒进入实验舱是合理的（净效用为正）"，S-3认为"任何未记录的行为都是违规"
- 处理方式：这是游戏最核心的叙事冲突，D-Agent会利用伦理矛盾推动玩家做出价值判断

### 7.2 矛盾解决流程

```
矛盾检测 → 分类 → 标记 → 呈现给玩家 → 玩家选择处理方式
    │                                        │
    │    ┌───────────────────────────────────┘
    ▼    ▼
┌──────────────────────────────────────────────┐
│  玩家可选的矛盾处理方式:                       │
│  1. 进一步质证 — 对相关Agent追问细节           │
│  2. 查询日志 — 寻找第三方证据                  │
│  3. 查看伦理线程 — 理解Agent决策动机            │
│  4. 接受一方说法 — 标记为"采信"或"否定"         │
│  5. 悬置判断 — 留待最终裁决时综合考虑           │
└──────────────────────────────────────────────┘
```

### 7.3 矛盾对游戏结局的影响

系统在后台维护一个"证据权重矩阵"，每条矛盾的处理结果都会更新该矩阵：

- 若玩家采信了某Agent的说法，该Agent的"可信度权重"增加
- 若玩家的最终结论与证据权重矩阵一致，获得"真相结局"
- 若玩家的最终结论与证据权重矩阵部分一致，获得"灰色结局"
- 若玩家的最终结论严重偏离证据，获得"错判结局"

## 8. 技术实现模式

### 8.1 消息传递层

推荐使用基于事件总线的异步消息传递，核心组件：

```python
class EventBus:
    """核心事件总线，所有Agent通信经由此处路由"""

    def __init__(self):
        self._subscribers: dict[str, list[Agent]] = {}
        self._audit_log: list[AuditEntry] = []
        self._message_queue: asyncio.Queue = asyncio.Queue()

    async def publish(self, message: GameMessage):
        """发布消息到总线，自动路由到订阅者"""
        # 1. 记录审计日志
        self._audit_log.append(AuditEntry.from_message(message))
        # 2. 写入共享状态总线
        SharedStateBus.append(message.to_state_entry())
        # 3. 路由到目标接收者
        targets = self._resolve_targets(message)
        for target in targets:
            await target.receive(message)

    def _resolve_targets(self, message: GameMessage) -> list[Agent]:
        """根据消息类型和权限矩阵确定接收者"""
        if message.msg_type == MsgType.PLAYER_ACCUSE:
            return [a for a in self._all_agents if a.id != message.target]
        elif message.msg_type == MsgType.PLAYER_ASK:
            return [self._get_agent(message.target)]
        # ... 其他消息类型的路由规则
```

### 8.2 Agent内部架构

每个机器人Agent内部采用"感知-推理-响应"三层架构：

```python
class RobotAgent:
    def __init__(self, agent_id: str, ethics_framework: EthicsFramework):
        self.agent_id = agent_id
        self.private_log: PrivateLog = PrivateLog()
        self.ethics_engine = ethics_framework
        self.perception_buffer: list[GameMessage] = []
        self.world_model: WorldModel = WorldModel()

    async def receive(self, message: GameMessage):
        """接收消息并放入感知缓冲区"""
        self.perception_buffer.append(message)
        self.world_model.update_from_message(message)

    async def generate_response(self, player_message: GameMessage) -> GameMessage:
        """生成对玩家消息的响应"""
        # 1. 感知层：解析玩家意图
        intent = self._parse_intent(player_message)

        # 2. 推理层：基于私有日志和伦理框架评估响应策略
        strategy = self._evaluate_strategy(intent, self.private_log)

        # 3. 伦理层：通过伦理框架过滤响应
        filtered_response = self.ethics_engine.apply(strategy)

        # 4. 响应层：生成自然语言输出
        return self._compose_response(filtered_response)
```

### 8.3 共享内存存储

使用结构化存储管理共享状态，支持版本追踪：

```python
class SharedStateStore:
    """共享状态存储，支持不可变追加和权限控制"""

    def __init__(self):
        self._entries: list[StateEntry] = []
        self._version: int = 0

    def append(self, entry: StateEntry) -> int:
        """追加条目，返回版本号（不可变原则）"""
        self._version += 1
        entry.version = self._version
        self._entries.append(entry)
        return self._version

    def query(self, filters: QueryFilters) -> list[StateEntry]:
        """按条件查询，自动应用访问权限过滤"""
        visible = [e for e in self._entries if self._check_access(e, filters.requester)]
        return apply_filters(visible, filters)

    def _check_access(self, entry: StateEntry, requester: Agent) -> bool:
        """权限检查：公开层全部可见，受限层需验证，私有层仅所属Agent"""
        if entry.access_level == AccessLevel.PUBLIC:
            return True
        elif entry.access_level == AccessLevel.RESTRICTED:
            return requester.has_restricted_access and entry.phase_unlock_met()
        else:  # PRIVATE
            return requester.id == entry.owner_id
```
